01 / formative study, N = 14

1/ The Gap & Formative Insights: PILOT

AI coding assistants are shifting from autocomplete into autonomous agents, and developers are increasingly running several sessions concurrently rather than working through tickets one at a time. This does not just add more agents—it adds a new layer of coordination and monitoring around them. We interviewed 14 developers who already work this way to understand how they cope, and distilled their strategies into the PILOT framework.

Fig. — Formative Survey
Parallel AI coding is already mainstream, not a niche habit

Self-reported time allocation across 14 developers who regularly run parallel AI sessions, sorted by parallel usage.

  • Parallel multi-session AI use (45.3%) is nearly on par with single-session AI use (48.6%); only 6.1% of coding happens with no AI at all.
  • CLI-based interfaces dominate (92.9% of participants), ahead of IDE-integrated chat and standalone web/desktop apps (78.6% each).
  • Copilot (78.6%) and Claude/Claude Code (71.4%) are the most-used tools; three concurrent sessions is the typical setup.
Fig. — "Compiling," Reframed
Waiting no longer means disengaging

P5 invoked the classic xkcd #303 trope to explain how parallel AI coding changes idle time.

  • Instead of legitimately stepping away while code compiles, developers stay actively engaged—monitoring, answering, and redirecting several concurrent agents at once.
  • Downtime becomes the trigger for opening another session, not a break from work.

Fig. — The PILOT Framework
Five supervisory practices, one shared bottleneck: attention

PILOT links two challenge areas—coordination (Plan, Isolate) and monitoring (Observe, Triage)—bridged by Logging, which preserves context across sessions.

P

Planning

Scope what to delegate, set priorities, and prep agent context before launching sessions.

I

Isolating

Decide what can run independently vs. what needs sequencing to avoid file conflicts.

L

Logging

Externalize memory—what each agent was asked, tried, and why—before it's forgotten.

O

Observing

Assemble a centralized view from makeshift terminals, monitors, and dashboards.

T

Triaging

Catch completions, clarification requests, errors, and unexpected delays before they're missed.

Summary

Developers already build ad hoc "control rooms"—terminal windows, markdown logs, custom dashboards, multi-monitor layouts—to coordinate and monitor parallel agents, but these workarounds stay brittle: sessions stall unnoticed, work gets lost track of, and context is hard to recover after switching away. PILOT synthesizes the five recurring strategies participants used to cope—the foundation for ParallelPilot.

02 / system

2/ ParallelPilot as a Design Probe

ParallelPilot is a supervision cockpit that instantiates PILOT as a lightweight layer over developers' existing agent CLIs, editors, and workspaces—rather than replacing them. It combines three integrated components, each mapped to complementary parts of PILOT.

Fig. — System Overview
Three components, mapped to PILOT

Tasks and specs feed into the planning interface; sessions launch and are automatically captured by the run-logger; the ambient dashboard synthesizes everything into a glanceable, triage-ready view.

Plan · Isolate

Planning Interface

Dependency-aware task preparation and scheduling across agent windows.

Log

Run-Logger

Automatic capture of per-agent events and traces—session memory that bridges coordination and monitoring.

Observe · Triage

Ambient Dashboard

Glanceable status, progress summaries, and cues for which session needs you now.

Fig. — Planning Interface
Dependency-aware plan structuring and iteration

Walkthrough persona Amelia pastes her tickets and codebase into ParallelPilot and clicks Analyze & Plan.

  • Task analysis (left): distinguishes independent work, shared-file conflicts, and output dependencies—automatically flagging that two tickets both touch the same file.
  • Execution timeline (center): organizes tasks across agent windows and waves, so sequencing respects those dependencies.
  • Assistant panel (right): lets Amelia compare alternative window configurations and settle on a supervision load she can manage.
Fig. — Ambient Dashboard
Glanceable status, attention cues, and direct terminal access

After stepping away, Amelia catches up in one glance: one ticket still running, one done and pending review, one needing her input.

  • Color-coded state per session—running, completed pending review, or needs input—so nothing sits stalled unnoticed.
  • Session memory and progress summaries make it fast to reconstruct context after an interruption.
  • Direct terminal access from the dashboard lets her review results and respond to the agent without losing the overview.

Summary

Rather than another chat client, ParallelPilot is built for the managerial vantage point of supervising a fleet: it externalizes the dependency map before work starts, passively preserves context while it runs, and actively surfaces what needs a human's attention—without asking developers to give up the CLIs and editors they already use.

03 / within-subjects study, N = 16

3/ Study Insights & Discussion

In a counterbalanced within-subjects study, 16 developers completed matched coding tasks with and without ParallelPilot. We measured objective throughput from logs, plus perceived coordination, monitoring, and control from surveys and interviews.

+63%tickets completed per minute vs. no-tool baseline
+1.50more tickets fully completed, on average
+1.69/7perceived efficiency (survey scale)
+2.06/7understanding of task dependencies
−1.88/7effort spent tracking parallel work
+2.56/7awareness of intervention cues
Fig. — Study Design
Counterbalanced within-subjects, project and order fully crossed

16 developers (4 groups of 4) each completed a ParallelPilot block and a baseline block, with condition order and project assignment (Sparkmatch / Kart) counterbalanced to rule out ordering and task effects.

  • Each block ran task intro, demo (ParallelPilot only), 20 minutes of live coding, and a post-block survey, bookended by consent and a closing interview.
  • Same task budget in both conditions isolates the effect of the tool itself, not extra time.
Fig. — Where the Time Goes
ParallelPilot raises the ceiling on how much parallel work feels manageable

Average time split between Plan & Isolate and Launch & Monitoring, with and without the tool.

  • Total time-to-done dropped from ~15.87 to ~12.43 minutes—faster in both phases, not just one.
  • Launch + monitoring time fell from 11.52 to 9.35 minutes; planning & isolating fell from 4.35 to 3.08 minutes.
  • Clearer decomposition: dependency-understanding ratings rose from 3.44 to 5.50 (q<0.001); perceived overlap/conflict between agents dropped from 3.06 to 2.13.
  • Lighter monitoring: tracking effort fell from 4.63 to 2.75, and disruption when switching sessions fell from 4.50 to 2.69—while awareness of stalls, completions, and questions went up.

RQ3 — The Boundary of Supervision

Better attention did not automatically buy back trust

Despite the gains above, perceived control (3.94→4.31) and self-rated intervention success (3.94→4.13) did not significantly improve. Confidence in interventions, output trust, and delegation confidence also stayed flat. When asked which condition made output easier to verify, 9 of 16 participants said no difference.

Making a fleet of agents observable is not the same as making its output verifiable—monitorability and trust are separable design problems.

Fig. — Exploratory Correlations
Coordination gains track productivity; monitoring gains track how efficient it feels

Per-participant gain with ParallelPilot on each RQ2 composite, plotted against RQ1 outcome gains (Spearman ρ).

  • Coordination gain (Plan + Isolate) correlates with more tickets completed (ρ=0.55, p=0.027) and higher throughput (ρ=0.62, p=0.010).
  • Monitoring gain (Log + Observe/Triage) correlates with perceived efficiency (ρ=0.62, p=0.011), but not with objective tickets completed or throughput.
  • The two supervisory halves of PILOT pay off in different currencies—coordination for measurable output, monitoring for how manageable the work feels.
Discussion
What this means for supervising parallel agents
  • Human management transfers, partly. Participants with prior management experience—engineering managers, PhD advisors—reused instincts like matching agents to tasks by "skillset" and running stand-up-style check-ins.
  • The abstraction tension. A higher-level view helps developers coordinate and monitor more agents at once, but by stepping back from implementation detail, it can leave them less equipped to judge whether the output is actually correct.
  • Design implication. Parallel coding tools need to connect high-level progress awareness with the implementation-level evidence developers still need to evaluate and redirect agent work—verification remains a fundamentally human task.

Contributions

  • PILOT—an empirically grounded framework of five supervisory practices for parallel AI coding, from a formative study of 14 developers.
  • ParallelPilot—a supervision cockpit operationalizing PILOT through dependency-aware planning, run-logging, and an ambient dashboard.
  • Empirical evidence from a controlled study (N=16) of higher throughput and lower tracking/context-switching burden—alongside a null result on perceived control that motivates connecting progress awareness to implementation-level evidence.
